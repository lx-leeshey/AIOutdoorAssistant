# AI 户外助手 · 产品需求文档（PRD）

> **状态：草稿 v0.1**
> 凡标注【假设】的段落都是推断，未经确认；带 ❓ 的是阻塞项，不解决就不能开工单。
> 本文件在 `AGENTS.md` 禁改清单内，只能由人修改。

---

## 0. 一句话定位

【假设】给长途骑行者的行程规划工具：**输入起点、终点、天数，输出每天骑多少、爬多少、住哪。**

## 1. 目标用户

【假设】

- 1–3 人的骑行小队，或独自长途
- 单次行程 3–15 天，跨城市
- 有基本骑行经验，会看海拔剖面
- **不是**：通勤用户、竞速训练用户、景区短途游客

## 2. 要解决的核心问题

【假设】现在排长途行程靠手工：翻地图算里程、查海拔、找住宿点、估每天能骑多远，一次要花几小时，而且经常排过头（第一天安排 150 km + 2000 m 爬升）。

## 3. 范围

### 3.1 做

- 按天数自动切分每日行程
- 每日里程、累计爬升、预计骑行时长
- 逐日调整
- 保存与回看

### 3.2 不做（明确排除，开工单时看到这些直接打回）

| 不做 | 理由 |
|---|---|
| 实时导航 / 语音播报 | 用户用手表或地图 App，我们做不过 |
| 训练计划、功率/心率分析 | 另一个产品 |
| 社交、组队、轨迹社区 | 冷启动做不起来，且是范围黑洞 |
| 装备电商 | 与核心价值无关 |
| 天气预警 | 第三方现成，最多做链接跳转 |

> **「不做」比「做」更重要。** 每加一条，就多一轮开发和维护。

## 4. 核心用户旅程

【假设】

1. 打开小程序 → 输入起点、终点、总天数
2. 系统返回每日分段草案（里程 + 爬升 + 住宿建议）
3. 用户逐日调整（改某天的终点、换住宿点）
4. 保存行程
5. 出发后查看当天安排

## 5. 功能清单与验收标准

> 验收标准必须能判对错。写不出「输入 X → 输出 Y」的，说明还没想清楚，不允许开工单。

| 编号 | 优先级 | 功能 | 验收标准 |
|---|---|---|---|
| P0-1 | P0 | 创建行程 | 输入起点、终点、天数（1–30），点生成后返回分段结果；任一字段为空或天数越界时给出明确提示，不产生空行程 |
| P0-2 | P0 | 生成每日分段 | 输出 N 个分段（N = 天数）；每段含起止点、里程（km）、累计爬升（m）、预计时长；各段里程之和与总路线里程误差 ≤ 5% |
| P0-3 | P0 | 行程详情页 | 可按天切换查看，每段显示里程、爬升、海拔剖面（有数据时）；无海拔数据时显示「暂无数据」而不是 0 |
| P0-4 | P0 | 保存与历史 | 保存后出现在列表；重新打开内容与保存时一致；删除后列表不再出现 |
| P1-1 | P1 | 逐日调整 | 可修改某天的终点，重算该天及之后分段；总天数不变 |
| P1-2 | P1 | GPX 导出 | 导出文件可被主流骑行码表导入，轨迹点数量 > 0 |
| P1-3 | P1 | 住宿点推荐 | 每天终点 5 km 内至少给出 1 个住宿候选；无候选时明确提示 |
| P2-1 | P2 | 行程分享 | 生成链接，他人可只读查看 |
| P2-2 | P2 | 离线缓存 | 行程详情在断网时可打开（至少已看过的） |

## 6. 非功能约束

| 项 | 约束 | 状态 |
|---|---|---|
| 地图与海拔数据源 | 需支持逐段爬升计算、有商用授权、配额够用 | ❓ 需 spike 验证 |
| 数据存储位置 | 境内，符合备案要求 | ❓ 取决于选型 |
| 弱网可用 | 山区信号差是常态，首屏不能依赖实时请求 | 待定 |
| 首屏时间 | 【假设】≤ 3 秒 | 待定 |

## 7. 验收方式

每个切片合并前，人手动走一遍该切片的主流程，逐条勾验收标准。
自动化测试覆盖验收标准里的硬指标（如里程误差 ≤ 5%）。

## 8. 待确认（阻塞项）

1. ❓ **平台**：微信小程序 / PWA / 双端
2. ❓ **后端**：微信云开发 / 自建服务
3. ❓ **域名备案**：现在做还是等
4. ❓ **GPX 导出**是 P0 还是 P1（影响是否需要文件存储）
5. ❓ 是否需要多用户协作（影响账号与数据模型）
6. ❓ 地图服务商预算上限（高德/腾讯/Mapbox 差异很大）

> 第 1–3 项不定，技术选型、目录结构、数据模型都无法开始。
